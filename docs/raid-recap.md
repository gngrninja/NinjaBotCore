# `/raid-recap` — private Retail raid review

## Use

- `/raid-recap` — resolve this Discord server's associated WoW guild by **server ID**, then choose a recent report.
- `/raid-recap guild:"Area 52, Example Guild, us"` — explicit `realm, guild[, region]`; default region `us`.
- `/raid-recap report:"https://www.warcraftlogs.com/reports/AbCdEfGh12345678"` — direct report URL or exact 16-character code. This code is synthetic.

Choose either guild or report. Guild lookup is read-only, independent of the Discord server's display name; missing/ambiguous associations require `/setguild` or an explicit target. Only Retail HTTPS hosts `warcraftlogs.com` / `www.warcraftlogs.com` are accepted. Arbitrary origins, other game hosts, URL credentials, malformed codes and whitespace repairs are rejected before lookup.

The panel is **private to its invoking user** in a normal server text channel. DMs/threads are unsupported. Both actor and bot must retain membership and View Channel access. `/logs`, `/watchlogs`, monitoring and guild-association writers are unchanged. The private recap has no patch-specific ability catalog, prediction or player-quality score. Automatic posting exists only in the opt-in live card described below.

## Presentation

The cards follow the `/char` WarcraftLogs views, so the two read as one product.

- **Header:** `# 📊 Raid Recap · <guild>`, the report title, then zone, difficulty, date and raid length. The Discord server icon is the thumbnail. Only HTTPS icon URLs are used. The guild name is shown when the report list was discovered for a guild; a direct report link has no guild name.
- **Navigation:** every button carries an emoji. The active view is green (Success) and the others are blurple (Primary), the same convention as `/char`. Tools (Reports, Refresh, Share overview) are grey (Secondary).
- **Parses:** one palette, `RaidRecapParsePalette`, serves both `/char` and `/raid-recap`. Gold 🟡 100, pink 🩷 99, orange 🟠 95, purple 🟣 75, blue 🔵 50, green 🟢 25, grey ⚪ below. A parse is shown as its dot and number, rounded down. A missing parse reads **no parse** and is never shown as zero.
- **Numbers and time:** output is compact (`1.23M`, `45.7K`). Durations and timestamps are `m:ss`, or `h:mm:ss` from one hour. Unknown values show `—`.
- **Footer:** `<guild> (REGION) | Data from WarcraftLogs · updated <relative time> · may still update`.
- **How to read:** every report view has a **How to read / Hide help** button beside the footer. All interpretation notes live there, so the cards stay short. Toggling it is local: it fetches nothing and changes no selection, page or public share. The report picker has no help control and rejects the action.
- **Select menus** show plain names. Card text is markdown and is escaped.
- **Pull strip:** the Bosses view and the *Still progressing* card show boss health left on each pull in order, latest twelve, such as `62 · 55 · 41 · 12 · ✅`. It is boss health, not phase. It is not on the public share.
- **Wording:** pulls, kills, wipes, best pull, last wipe, deaths, kicked, went off, dispelled. Partial results are marked **Partial data** and their counts read **at least**.

The sections below describe behaviour, limits and safety rules. Where they quote older labels, the labels above are current.

## Live card

`/raid-recap-live` posts one public card when the guild's raid log goes live and keeps editing that same message until the raid ends. Edits never ping anyone.

**States**
- **Found:** one of the guild's three newest logs had an event in the last 15 minutes and has at least one raid boss pull (LFR, Normal, Heroic or Mythic). Dungeon logs and logs with only trash are ignored. The card is posted, marked 🔴 LIVE. The report is claimed in the database before posting, so two bot processes cannot both post it.
- **Watching:** the log is re-read every 90 seconds. After 10 minutes without a new pull that slows to every 3 minutes, and speeds up again with the next pull. The message is edited only when what it shows has changed.
- **Ended:** the log has been quiet for 30 minutes, or the card has been watched for 8 hours. The card becomes a final summary, marked 🏁, and watching stops. If the same log goes live again within those 8 hours, for example after a long break, the same card returns to 🔴 LIVE.
- **Stopped:** the card was deleted, the server turned the feature off, the rollout stopped covering the server and the card went quiet, or 10 refreshes in a row failed. A refresh refused because the WarcraftLogs budget is spent does not count as a failure. A deleted card is never reposted. Otherwise the card is edited to say updates stopped, so it never claims to be live forever.

**What the public card shows**
- Kills, wipes, pulls, time on bosses, and each boss with its result. The log's title is left out, because it is free text typed by the uploader.
- The current boss, the last pull, the best pull, and a pull strip such as `62 · 55 · 41 · 12 · ✅` (boss health left per pull, latest 12).
- The first three deaths of the latest wipe, shown by **spec and class only**, never by name or link.
- The top three damage and healing of the latest kill, shown **by name** with spec, class and parse. Being listed there is praise. A name is linked to the player's view of the kill only when the player was matched to the raid roster.
- **Open my recap** opens the private `/raid-recap` for that log, for whoever pressed it, on the latest pull's deaths. Its custom ID holds only the report code, so it keeps working after a restart.

**Two switches**
| Switch | Who | What |
|---|---|---|
| `/raid-recap-live state:` On, Off or Status, optional `channel:` | Officers (Kick Members, same as `/watchlogs`) | Turns the card on or off for the server. The channel defaults to the `/watchlogs` channel, then to where the command was run. Needs `/setguild`. |
| `/raid-recap-rollout mode:` Off, My servers, Everyone or Status | Bot owner only | Chooses which servers are eligible. Off is the kill switch: the watcher makes no WarcraftLogs calls and no Discord calls. **Open my recap** on cards already posted still works, the same as running `/raid-recap`. Hidden from help. |

**Rollout gate.** In *My servers* mode a server is eligible only while the bot owner is a member of it. The bot already holds each server's member list, so the check normally costs no Discord call. Right after a restart, while member lists are still downloading, it asks Discord directly. Joining a server makes it eligible and leaving removes it. The default mode is *My servers*, and nothing is posted anywhere until an officer turns the card on.

**Cost and limits**
- One log read per refresh. Deaths and top output are read again only when the latest wipe or the latest kill changes, each independently.
- Roughly 120 to 160 API points per live raid per hour. These are estimates from third-party measurements.
- At most 20 cards are refreshed at once across all servers.
- Servers without a live card are checked for a new log every 5 minutes, at most 5 servers per sweep, longest-waiting first.
- The bot needs View Channel, Send Messages and Read Message History in the card's channel.
- The card reads through the same caches as the private recap.

**State** is in three tables: `RaidRecapLiveSettings` (per server), `RaidRecapLiveCards` (one row per posted card, unique per server and report) and `RaidRecapRollout` (one row). Watching resumes after a restart. Migration: `AddRaidRecapLive`.

The existing `/watchlogs` "New log" post is unchanged.

## Five main views

**Overview** opens with a short snapshot synopsis and up to two private, native CV2 **Worth a look** cards, not a repeated encounter wall. The first prioritizes the most-pulled unresolved encounter/difficulty (ties resolve by encounter ID, then difficulty), with an exact latest-wipe death link and local **Details** navigation to its chronological attempts. If no completed wipe exists, it links the latest attempt without inferring its outcome. The other is labeled **What changed?**, not “latest”: it can deliberately prioritize an older wipe → kill over a newer wipe pair, within one encounter or across encounters. Prefer the latest immediately adjacent wipe → kill within an encounter/difficulty, otherwise the latest two eligible completed pulls. Across groups, wipe → kill pairs take precedence, then the most recent pair. An intervening live/unknown/unsupported attempt is not silently skipped to claim an immediate wipe → kill. Details opens A/B selectors without loading analysis. No-fights, single-pull and unsupported/no-pair states explain what is missing. These are observations/questions, not causal recommendations, grades, success colors or scores. `bossPercentage` is active boss health, not encounter completion.

Card actions carry only a local card slot. The service recomputes its target from the owning session snapshot; arbitrary supplied fight IDs are not accepted. Sharing still uses the **previous metadata-only overview**, not these private cards.

**Bosses** separates encounter ID and difficulty. All attempts are reachable in chronological pages of ten, including short wipes and unfinished/unknown attempts. Each links to its exact fight and shows outcome, elapsed duration and active boss health. Statistics are descriptive:

- Completed combat time sums available durations of completed kills/wipes, with known/eligible sample counts. It is not the report span or “wasted time.”
- Median completed-wipe duration uses every known positive completed-wipe duration, including short wipes, and shows known/eligible `n`. Missing durations are not zeros.
- Best wipe active boss health is the minimum known wipe value; latest wipe health refers to the latest wipe even when its health is unknown. Fastest kill uses known completed-kill durations.
- No prediction, cross-boss trend or silently filtered attempts.

### Matched pulls (inside Bosses, not a sixth tab)

The **Compare** section accessory opens two explicitly labeled selections, **A** and **B**. **All pulls** returns to the unchanged chronological view; Damage, Healing and Analysis remain top-level tabs. Eligible pulls must have distinct positive fight IDs, completed kill/wipe outcomes, a positive encounter ID, the same known positive difficulty, and finite positive durations. Trash, live/unknown outcomes, missing/nonfinite durations, unknown difficulty and duplicate identities are not comparison candidates. Initial pair selection follows the rule above within the selected boss group.

Both selectors page through every eligible pull in chronological order, 25 options per page, with independent **A previous/next** and **B previous/next** controls. Paging changes available options only, never either selection or its analysis. The selected A/B fight labels remain visible even off-page. Off-page, same-fight and forged values are rejected server-side. Each side shows elapsed duration, Kill/Wipe, descriptive active boss health and its exact WCL death-view link. No percentages of encounter completion are inferred.

**Compare deaths** is a separate deliberate load. It requests at most the two selected existing full-pull `deaths` analyses, reusing exactly the Analysis cache keys, snapshot checks and collection budgets. It does not query a new clipped range or truncate the primary Analysis timeline at the first death. The summary shows:

- Separate full-pull death-event counts and distinct player counts for A and B, with complete/partial observation status.
- The common elapsed window **[0, min(A duration, B duration)]**, including both endpoints. Events beyond that window remain in the full-pull counts and primary Analysis view.
- Within that same window, event and distinct-player counts; when both results are complete, descriptive **B − A** count changes and first-loss timing/ties for each scope. Repeated deaths of the same player increase event counts, not distinct-player counts.

Equal elapsed time does **not** establish equal phase, opportunity, roster or strategy. First loss is not a cause or blame verdict. The private comparison links up to three first-loss players per pull, reports every simultaneous-player total, and offers **All first deaths** with locally paged complete ties. The public overview still contains no player names. If either side is partial, retained counts are explicitly observations/lower bounds; all numeric changes and definite first-loss claims are withheld. Missing or failed results are never interpreted as zero. A failed fetch (including the second side), mismatched metric or snapshot drift discards the whole comparison rather than mixing potentially different snapshots; open the exact WCL links or deliberately retry/refresh. Previously cached valid sides can be reused on retry, but are not displayed as a completed comparison after a failure.

The old comparison is cleared **before** a comparison load awaits and in the command error path. Changing a selection, boss/report, refreshing or leaving the subview clears it. Selector pagination alone retains it. Rendering additionally checks snapshot and selected-fight identity. Added session state is fixed-size: one pair, two option-page indices and one result holding at most two already bounded analyses. No new cache, database, dependency or background work is introduced.

**Damage / Healing** selects one completed boss kill; sources are ordered by returned total divided by the **whole kill's elapsed seconds**. Wipes/trash/live/unknown outcomes are not throughput rankings. Sources are packed as whole native CV2 cards, at most five per page and within the escaped-text budget. Each sibling card uses its validated overall WCL parse band as its actual accent; the parse dot and number remain readable. Unknown parses use neutral styling, never a fabricated gray-zero percentile. Raw output order is preserved across pages. Damage owner totals already include pets in the sampled source view: nested pets are never added again. Healing is WarcraftLogs' healing table total divided by elapsed seconds; How to read says so and makes no effective-healing claim. Overheal is not added, and `totalReduced` is not substituted. These raw rates are not active-time rates, cross-fight averages, parse percentiles or player grades. Separately labeled WCL percentiles are described below.

The scan-first header retains the selected kill, its length, exact fight link and all warnings. **How to read / Hide help** locally discloses output position versus parse, pet accounting, no cross-fight averaging, complete band thresholds, non-inflating display policy, partition/parse as-of and finality caveats. Snapshot freshness remains visible while collapsed. Toggling neither fetches provider data nor changes the kill, source order, source page, notices or public sharing. Pages reserve space for expanded help, so toggling never silently repacks sources. Help starts closed and resets on a report/refresh/main-view/fight change or entry into Players; source/kill-option paging retains it. Hidden help actions outside the main Damage/Healing views are rejected, and all actions retain the existing ownership, expiry, generation, permission and final-edit gates.

**Previous players / Next players** occupy one actual action row; the pair is omitted for a single page. The help control sits beside the footer. **Previous kill options / Next kill options** appear only above 25 options, in their own row. Option browsing leaves the selected kill and source page untouched and makes no provider request; the selected kill remains in the header when off-page. Rows are built in deterministic order because Discord.Net inserts absent row indices instead of reserving them. The same narrow ordering correction keeps Bosses' attempt pair and the unselected Players catalog's option pair together; no navigation or permission redesign is involved.

**Analysis** works on one completed kill **or wipe**. Entering from Bosses prefers that encounter/difficulty's latest completed pull, otherwise a completed pull is selected. The paged picker labels boss, difficulty, Kill/Wipe and fight ID. Paging the picker changes available options, not the analyzed pull; only explicitly selecting a pull changes scope. Five subviews occupy one row:

- **Deaths:** observed player-death events, distinct players, elapsed `m:ss` timestamps in event order, simultaneous first-death ties and repeated death-event ordinals. `killingAbility` supplies the recorded killing blow; missing ability stays unknown. Only targets belonging to both the selected fight's `friendlyPlayers` and validated master-data `Player` actors are included. Pets/enemies are excluded. Missing roster is unavailable; missing identity is visibly partial. A known-empty complete result says no player deaths. Partial results report only observed events and do **not** claim a definite first loss. Inspect lead-up damage, healing, defensives and assignments in the linked WCL death view. First death/killing blow is not a cause or blame verdict; cooldown availability/preventability are not inferred.
- **Damage taken** (action `incoming`): WarcraftLogs damage-taken table totals by top-level ability/source, descending. Composite parent totals are used once, without summing nested subentries or replacing `total` with `totalReduced`. Mitigation/absorb semantics are not validated as net/effective damage. Check assignments, soaks and mitigation against major sources in WCL; this is not an avoidable-damage score or an HP/opportunity denominator.
- **Interrupts:** successful observed `spellsInterrupted`, WCL-reported `spellsCompleted`, and separate `spellChannelsInterrupted`. These fields are never added together. Spell rows and returned participant `details[].id/name/total` are paginated without recursively adding nested pets. Missing/inconsistent attribution is shown as unavailable/unassigned. Completed casts are not missed assignments; not all casts are interruptible. Review cast timing and assigned rotation.
- **Dispels:** observed successful `spellsInterrupted` from WCL's nested dispel table, with attributed participants and explicit missing/unassigned attribution. Remaining applications are not failed obligations. Review timing, strategy and assignments. No coverage percentage or expected-action denominator.
- **Mechanics:** selected-rule Lost Explorers damage-event / debuff-application evidence, with scope and coverage gates described below. Unsupported fights do not produce successful zero counts.

All analysis subviews link to the selected fight and exact WCL view. Detail rows are paged eight at a time, including every retained participant row. Five main tabs, a pull menu, five subview controls, and separate pull/row pagination fit five action rows. Names are Unicode-aware, mention-neutralized, Markdown-escaped and bounded after escaping.

### Mechanics: one narrow Lost Explorers pack

**Mechanics** is the fifth Analysis subview, not a sixth main tab. One native CV2 Section names the selected rule and its button switches to the other (**Throw Junk** / **Shell Spin**), which keeps the card inside the component budget. Entering Mechanics selects the remembered mechanic or defaults to Throw Junk. Other Analysis subviews do not load mechanic metadata or streams. Picker/row pagination is local-only; selecting a different pull loads only the selected rule for that pull. The old result is cleared before awaited loads/report changes and by command errors. Rendering also checks the selected metric, snapshot, fight ID and full range, so an old mechanic result cannot appear under a new selection.

Pack version: `lost-explorers-3497-heroic-observed-events-v1`. Admission is deliberately limited to encounter **3497**, difficulty **4 (Heroic)**, `masterData.gameVersion=1`, principal report zone **53**, expansion **7**, and fight `gameZone.id=3004`. Both `kill` outcomes are admitted only when explicitly boolean, `inProgress=false`, `completeRaid=false`, and the selected range is positive, finite and unchanged. Archive access must be explicitly accessible. Unknown/other game, encounter, difficulty, zone or completion metadata is **unsupported**, not successful zero. Missing/denied/malformed required data or snapshot drift is **unavailable**. `logVersion=17` in research is an uploader/parser version, **not** an exact client build or patch gate; no client build was established.

- **Throw Junk damage events**: numeric spell **1291935**, `dataType: DamageTaken`, count only matching `damage` rows. A zero-amount, fully absorbed row still counts. Amount and absorbed are separate optional normalized context, not a required numerator, a sum or a score.
- **Shell Spin debuff applications**: numeric spell **1291918**, `dataType: Debuffs`, count only matching `applydebuff` rows. Removals, refreshes, stack updates, casts, summons and same-spell damage are not applications. No “stuns”, position failures, duration, avoidability or opportunity percentages are inferred.

Every counted row must match numeric `abilityGameID`, selected fight ID and requested report-relative timestamp range, and join both the selected roster and exactly one validated Player actor. Known Pets/NPCs are excluded, never attributed to owners. Missing/invalid targets, unresolved identity or out-of-roster Players make observations partial. Duplicate/conflicting actors or roster IDs reject metadata. The provider's numeric Environment sentinel `id=-1,type=NPC` is a recognized nonplayer, never a Player or roster member. Names are bounded to 80 Unicode runes before cache retention and escaped/truncated again for display.

The selected rule shows event count, distinct affected players, **full-pull duration**, the count definition, a neutral review question, and every retained affected-player row in pages of eight with elapsed `m:ss` timestamps. Its evidence link specifies the exact WCL fight, view and numeric spell. Timestamp hash routing is **not** claimed verified. Simultaneous and repeated complete event rows are retained; there is no invented incident deduplication. **Complete zero** requires a valid empty event array, present null cursor, validated scope/roster/identity and stable snapshot. **Partial** counts/distinct players are lower-bound observations; no definite zero is inferred. This slice does not add cross-pull mechanic comparison, a timeline engine, cooldown/consumable analysis or expected-opportunity models.

Mechanic metadata is fetched lazily only for the selected rule/fight. The fixed metadata document omits the report-wide ability catalog and leaves the default report loader unchanged. Typed event requests set `abilityID`, `useAbilityIDs:true`, `useActorIDs:true`, `killType:All`, `hostilityType:Friendlies`, `wipeCutoff:0`, `includeResources:false`, `translate:true`, and `limit:100`. **Do not replace these with `dataType:All + abilityID`**: that combination was empirically unfiltered. Five event pages, **500 total raw rows** (including nonapplication/nonplayer rows), the shared **4 MiB decoded-body cap per response**, and one **30-second deadline covering metadata, OAuth/quota and all event fetches** bound a load. There is no new unbounded metadata cache. Roster and actor ceilings are 100 and 2,000; returned fight metadata is capped at 100 rows with unique IDs and an exact selected-fight match.

The original end/fight/filter scope is fixed across pages; each valid cursor is copied unchanged. Empty/short pages do not prove completion. Missing/wrong-type, repeated/backward, out-of-range or last-row-equal cursor patterns stop as incomplete rather than guessing advancement. Initial malformed event data is unavailable; later fetch/body/deadline exhaustion can retain lower-bound rows. Caller cancellation propagates. A changed/missing code, revision or report end time discards **all** accumulated pages rather than retaining a mixed-snapshot partial. Only normalized observations enter the existing bounded cache; raw HTTP bodies/JSON do not.

## Players and verified parse context

**Players** is a private subview, not a sixth main tab. It occupies the fifth normal tool-row slot; comparison retains **All attempts** instead, never six buttons. Overview/Bosses require an explicit completed-pull choice. Damage/Healing and Analysis can reuse their explicitly displayed current kill/pull. Only bounded roster/identity metadata is loaded on entry; no death stream or bundle of metrics is fetched to discover players.

The catalog retains all validated selected-pull Player actors, including those without observations (cap 100). Actor IDs, not names or output positions, are selection keys. Only duplicate names carry `#actorId` labels. Initial player selection is empty. Catalog pages contain at most 25 options and do not change the selected actor, lens, evidence page or pull. Off-page/forged selections are rejected. The selected player stays visible when its option is off-page. Boss/kill option pagination likewise no longer silently changes the selection or fetches data. Source-row and player evidence pagination are local-only.

**Summary** uses only already loaded normalized results. It distinguishes not-loaded, partial/unsupported, and complete observations. The lens picker explicitly requests one of Damage, Healing, Deaths, Interrupts, Dispels, Throw Junk or Shell Spin. Damage/Healing require a completed kill; wipes are not zero parses. Whole-pull caches are shared across actors and sessions; selecting another player filters locally, never starts another event stream. Mechanics use only the existing verified rule pack. Incoming remains a fight-wide outbound evidence handoff, not a fabricated personal total. Back restores the origin without reloading; changing pull, refreshing and report changes clear player-scoped state before awaits. Failed lenses remove the old result and permit deliberate retry; public share always uses the unchanged metadata projection.

Death/mechanic collectors already validate local actors; utility attribution now requires the same selected-roster validation before linking. ### WCL percentiles, not output positions

Selected-kill enrichment explicitly requests **`compare: Parses`, `timeframe: Today`, `playerMetric: dps|hps`**. The provider JSON scope must match fight, encounter, difficulty, duration, numeric kill marker, partition and report snapshot. `reportsBlacklistForCharacters` must be an empty array. Unsupported/malformed scope and unfamiliar character-row fields fail closed. Provider `rankPercent` is the overall percentile; `bracketPercent`, when valid with bracket/item-level metadata, is separately labeled **ilvl parse**. `totalParses` is the overall comparison population, never the bracket sample count. No approximate ordinal is relabeled world rank, no bracket width is inferred, and no final/locked claim is made.

Rankings use global character IDs, distinct from local actor IDs. The bridge requires unique exact name, region, provider-normalized realm, class, selected-fight single spec and validated role. It cross-checks playerDetails and master actor metadata numerically against the selected roster. Only server IDs referenced by rankings are queried, in one parameterized alias document (at most 25). Realm display name and region must agree with authoritative `worldData.server`; no local punctuation stripping or name-only fallback exists. Missing/ambiguous canonical identity omits the parse but not valid raw output.

A numeric **0** percentile is real; null, boolean, string, nonfinite, negative, >100 or zero/malformed population is unavailable. Gray starts at 0, green 25, blue 50, purple 75, orange 95, **pink 99**, and **gold exactly 100**. Fractional displays floor as NinjaBot's non-inflating policy; this is not a claim about WCL's own rounding. Colors have numeric/band labels; raw output order is never colored as a parse. A source card or individual player card's native accent represents its verified overall percentile; missing parses use neutral accents with no scoring meaning. Today stays visible on source headers; parse as-of/partition are available in How to read and may change independently of report revision. Optional parse/network failures retain raw output and failed enrichment is not cached as success; snapshot drift still fails visibly. Caller cancellation remains supported on the direct provider APIs.

Private report views use sibling native CV2 containers, not nested containers or arbitrary text RGB. Damage/Healing have a scope/navigation container, a concise selected-kill header, up to five independently accented source containers, and a compact control/help container; other views retain their scope/navigation and evidence containers. The report picker likewise separates its scope from compact metadata-only choices. Test budgets count Sections, their children and accessories: **40 components**, **five action rows**, and **3800 aggregate Text Display characters after escaping and link insertion**. Whole-row packing retains every admitted observation and repeats spell context on participant continuation pages. Public overview layout/text remain unchanged.

## Loading, limits and honesty

Recent report discovery is metadata-only (up to 100 reports, 25 menu options per page). Direct report URLs reach older reports. Opening reports, using Review first Details, navigating Overview/Bosses/Matched pulls or paging either comparison selector or Analysis pull options does not query analysis tables/events. Death actor/roster metadata is fetched lazily with the first requested death page, not for every report.

All detail requests use the fixed Retail WCL origin, variables for the exact report/fight/range, and explicit nonzero report-relative start/end times. Throughput sets `killType: Kills`, `viewBy: Source`; Analysis tables set `killType: All` and `viewBy: Ability` for DamageTaken or `Source` for Interrupts/Dispels. Utility parsers use observed nested `data.entries[].entries[]`, not a flat player table. Counts must be finite, nonnegative integers.

Death events set `dataType: Deaths`, `limit: 100`, `useActorIDs: true`, `useAbilityIDs: false`, one fight ID and its unchanged end time. The next request copies `nextPageTimestamp` exactly: no epsilon. Five pages / 500 raw event rows / a 30-second analysis deadline bound collection. A page may contain more than the requested limit (observed live); only the hard global row ceiling truncates it. A valid null cursor establishes completion, not a short page. Missing, backward, repeated or unsupported overlapping cursors, invalid rows, missing identity, errors or exhausted limits never become a complete zero. Previously valid rows may be retained as partial; snapshot drift discards the entire analysis.

Incoming is capped at 500 top-level rows. Utility is capped at 100 outer groups, 500 inspected nested rows, 100 participant entries per spell and 1,000 participant entries overall. Truncation is visible as partial. Actor metadata is capped at 2,000 entries and the selected roster at 100. Cached objects retain normalized observations and bounded names, never raw event/table JSON. Streamed HTTP response size and OAuth/HTTP cancellation are enforced by the shared WCL transport; oversized responses are unavailable/partial, never empty results.

Every detail response, including mechanic metadata and every death/mechanic page, must match report code/revision/end time. These checks detect drift; there is no remote immutable-revision selector. Every panel includes its original **as-of** time and “may still update.” Report `endTime` is a last-event timestamp, not evidence that raiding is finished.

Process-local cache: 128 entries including in-flight work; guild/report metadata TTL 30 seconds, normalized detail TTL two minutes. Keys include snapshot code/revision/end/as-of, fight/range, metric and analysis options; parse enrichment additionally separates DPS/HPS, Parses/Today and the provider-selected partition request, with the actual selected partition retained in the immutable result. Today uses its own two-minute freshness, not report revision as a lock. Bounded roster identity is shared between player entry, throughput and attributed utility; mechanics additionally keys the fixed pack version and full-pull / Player-target / ID-mode / hostility / wipe-cutoff policy. Concurrent identical loads single-flight; active loads are not evicted to start duplicates. Failed loads clear their entries; bounded partial observations are cached for the same TTL, so immediate retries can retain the same partial result. Refresh is on demand and subject to the metadata TTL. Restart clears cache and sessions.

## Privacy and authority

Sessions: at most 256, ten-minute lifetime, random tokens bound to actor/server/channel. Generations reject stale queued controls. Transitions hold their gate through final editing; permissions/currentness are checked after provider waits. CV2 edits clear legacy content/embeds, set ComponentsV2, and suppress mentions.

**Share overview** is still the only public action. It publishes a read-only Overview to the originating channel, never Review first cards, matched-pull comparisons, Mechanics, Deaths, Incoming, Interrupts, Dispels, source rankings, private notices or session tokens. Sharing requires current View Channel / Send Messages rights for both participants, and fresh actor timeout/current-session checks at the actual send boundary. A timeout does not remove private analysis access. One share attempt per session; ambiguous sends are not retried. Public sends suppress mentions and use `RetryMode.AlwaysFail`. No permission or session gate is relaxed by Analysis.

## Exact-query capture and offline replay

`RaidRecapPlayerQueryReplayTests.CaptureSourceQueriesAndReplaySuppliedExactResponsesThroughHttpServiceAndSdk` always exercises an explicitly synthetic source/HTTP/service/SDK fixture in the normal suite. The handler captures exact production `<Name>.query.graphql` and `<Name>.variables.json` before demanding `<Name>.response.json` in the input directory. Complete requires actual nonempty verified parses for both metrics, all retained sources reachable in original order through every source page with help both open and closed, no new provider requests from this navigation, rendering budgets, and byte-identical metadata-only sharing after private enrichment.
